# API Gateway Scaling Design


## chunk_id
- 7.26

## category
- infrastructure_components

## type
- infrastructure_component

## definition
- designing horizontal and regional scaling for api gateways while preserving auth policy consistency, latency budgets, and failure isolation.

## when_to_use
- gateway handles high fan-in from many clients and products
- edge traffic varies heavily by region and time
- gateway enforces heavy cross-cutting concerns (auth, quota, transform)

## when_not_to_use
- low-traffic internal systems with static routing needs
- architectures where each service already owns public ingress

## decision_signals
- need: gateway handles high fan-in from many clients and products
- need: edge traffic varies heavily by region and time
- willing to accept: policy distribution and config rollout complexity

## advantages
- sustains growth without central bottlenecks
- improves resilience via regional isolation and autoscaling

## disadvantages
- policy distribution and config rollout complexity
- noisy-neighbor traffic can still impact latency if quotas are weak

## anti_patterns
- scaling stateless replicas without scaling auth/cache dependencies
- sharing one global rate-limit bucket for unrelated tenants
- deploying config changes globally without staged validation

## real_world_examples
- regional gateway pools with per-tenant throttling and local auth caches
- separate public and partner gateway fleets with different slos

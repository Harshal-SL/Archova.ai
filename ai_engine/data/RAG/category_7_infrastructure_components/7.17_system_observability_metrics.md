# Observability: Metrics


## chunk_id
- 7.17

## category
- infrastructure_components

## type
- infrastructure_component

## definition
- numeric time-series measurements (latency, error rates, saturation) used to monitor health and drive alerts and scaling.

## when_to_use
- defining slos and alerting on user-impacting issues
- capacity planning and autoscaling decisions
- detecting regressions after deploys

## when_not_to_use
- when metrics would be high-cardinality and unaffordable to store
- when alerts cannot be acted upon and would create noise

## decision_signals
- need: defining slos and alerting on user-impacting issues
- need: capacity planning and autoscaling decisions
- willing to accept: high-cardinality labels can explode cost and storage

## advantages
- enables fast detection of issues via dashboards and alerts
- supports trend analysis and forecasting

## disadvantages
- high-cardinality labels can explode cost and storage
- poorly tuned alerts cause fatigue and missed incidents

## anti_patterns
- use this when metrics would be high-cardinality and unaffordable to store
- use this when alerts cannot be acted upon and would create noise
- ignoring the downside that high-cardinality labels can explode cost and storage

## real_world_examples
- tracking p95 latency and error rate per endpoint and region
- alerting on queue lag growth rate and database saturation

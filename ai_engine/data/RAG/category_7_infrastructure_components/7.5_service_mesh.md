# Service Mesh


## chunk_id
- 7.5

## category
- infrastructure_components

## type
- infrastructure_component

## definition
- an infrastructure mesh stack implemented with Istio, Linkerd, or Consul Connect using sidecar proxies for mTLS, traffic shaping, retries, and telemetry.

## when_to_use
- many services needing consistent traffic policies and security
- requiring mutual tls and fine-grained service auth
- needing uniform metrics and tracing without app changes

## when_not_to_use
- small systems where operational complexity would outweigh benefits
- latency-sensitive systems where proxy overhead is unacceptable

## decision_signals
- need: many services needing consistent traffic policies and security
- need: requiring mutual tls and fine-grained service auth
- willing to accept: adds operational complexity and new failure modes

## advantages
- centralizes network policy and security controls
- improves observability and traffic management consistency

## disadvantages
- adds operational complexity and new failure modes
- debugging requires understanding proxy behavior and configs

## anti_patterns
- using this for small systems where operational complexity would outweigh benefits
- using this for latency-sensitive systems where proxy overhead is unacceptable
- ignoring the downside that it adds operational complexity and new failure modes

## real_world_examples
- enforcing mTLS between services and rotating certificates automatically
- using Istio VirtualService rules for canary and failover traffic splitting

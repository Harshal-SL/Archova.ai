# Input Validation and Sanitization


## chunk_id
- 9.11

## category
- security_architecture

## type
- security_pattern

## definition
- validating and normalizing inputs at boundaries to prevent injection, deserialization issues, and unexpected states.

## when_to_use
- any public api or user-controlled input surface
- systems that process files, templates, or untrusted payloads
- preventing data corruption and downstream vulnerability chains

## when_not_to_use
- when inputs are already strongly constrained and validated at a single trusted boundary (still validate critical invariants)
- when validation rules are unknown and would block legitimate traffic

## decision_signals
- need: any public api or user-controlled input surface
- need: systems that process files, templates, or untrusted payloads
- willing to accept: complex rules can be hard to maintain and can introduce false positives

## advantages
- reduces vulnerability exposure and improves correctness
- prevents bad data from entering persistence and pipelines

## disadvantages
- complex rules can be hard to maintain and can introduce false positives
- inconsistent validation across services can cause drift

## anti_patterns
- use this when inputs are already strongly constrained and validated at a single trusted boundary (still validate critical invariants)
- use this when validation rules are unknown and would block legitimate traffic
- ignoring the downside that complex rules can be hard to maintain and can introduce false positives

## real_world_examples
- schema-validating json payloads and rejecting unknown fields
- sanitizing user-provided html and enforcing file type allowlists

# Secure-by-Default Headers and CSP


## chunk_id
- 9.21

## category
- security_architecture

## type
- security_pattern

## definition
- using security headers and content security policy (csp) to reduce browser attack surface like xss, clickjacking, and mixed content.

## when_to_use
- web applications and browser-based admin consoles
- preventing script injection and UI redress attacks
- standardizing security posture across web frontends

## when_not_to_use
- when csp is treated as a one-time change without monitoring and tuning
- legacy apps that cannot be updated and would break without phased rollout

## decision_signals
- need: web applications and browser-based admin consoles
- need: preventing script injection and UI redress attacks
- willing to accept: csp can be complex to deploy without breaking legitimate scripts

## advantages
- blocks whole classes of browser attacks when configured correctly
- provides defense in depth beyond input validation

## disadvantages
- csp can be complex to deploy without breaking legitimate scripts
- requires ongoing monitoring and policy refinement

## anti_patterns
- use this when csp is treated as a one-time change without monitoring and tuning
- using this when legacy apps that cannot be updated and would break without phased rollout
- ignoring the downside that csp can be complex to deploy without breaking legitimate scripts

## real_world_examples
- enforcing strict csp with nonces and disallowing inline scripts
- setting frame-ancestors to prevent clickjacking

# Secure Configuration and Hardening


## chunk_id
- 9.15

## category
- security_architecture

## type
- security_pattern

## definition
- reducing attack surface by disabling unsafe defaults, tightening configurations, and enforcing secure baselines across environments.

## when_to_use
- production environments and internet-facing services
- container, vm, and kubernetes cluster baselines
- reducing risk from misconfiguration and exposed services

## when_not_to_use
- when changes are untested and could disrupt availability without rollback
- environments that cannot enforce configuration drift control

## decision_signals
- need: production environments and internet-facing services
- need: container, vm, and kubernetes cluster baselines
- willing to accept: hardening can break legacy integrations and tooling

## advantages
- prevents whole classes of known misconfiguration vulnerabilities
- improves consistency and compliance across fleets

## disadvantages
- hardening can break legacy integrations and tooling
- baseline drift can reintroduce risks without enforcement

## anti_patterns
- use this when changes are untested and could disrupt availability without rollback
- using this when environments that cannot enforce configuration drift control
- ignoring the downside that hardening can break legacy integrations and tooling

## real_world_examples
- disabling public access to databases and restricting inbound ports
- enforcing tls-only, secure headers, and minimal cipher suites

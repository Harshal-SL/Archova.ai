# Secrets Management and Rotation


## chunk_id
- 9.5

## category
- security_architecture

## type
- security_pattern

## definition
- storing secrets securely and rotating them regularly so credentials are not embedded, long-lived, or widely shared.

## when_to_use
- api keys, database passwords, signing keys, and certificates
- reducing credential leakage and meeting security controls
- supporting automated deployments and ephemeral environments

## when_not_to_use
- when secrets can be replaced with short-lived identity tokens instead
- when rotation is untested and would likely cause outages

## decision_signals
- need: api keys, database passwords, signing keys, and certificates
- need: reducing credential leakage and meeting security controls
- willing to accept: rotation can break services if dual-validity is not supported

## advantages
- reduces risk and exposure duration of leaked secrets
- improves operational hygiene through rotation and auditing

## disadvantages
- rotation can break services if dual-validity is not supported
- secret distribution becomes a critical dependency

## anti_patterns
- use this when secrets can be replaced with short-lived identity tokens instead
- use this when rotation is untested and would likely cause outages
- ignoring the downside that rotation can break services if dual-validity is not supported

## real_world_examples
- rotating database credentials with an overlap window and staged rollout
- issuing short-lived certificates for mTLS between services

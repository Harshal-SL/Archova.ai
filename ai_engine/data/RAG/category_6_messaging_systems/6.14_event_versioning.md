# Event Versioning

## chunk_id
- 6.14


## category
- messaging_systems

## type
- messaging_pattern

## definition
- evolving event formats over time while keeping older consumers functional via compatible changes, version fields, or new event types.

## when_to_use
- long-lived event streams with many consumers
- adding fields or changing semantics over time
- migrating from one payload format to another

## when_not_to_use
- when events are internal and tightly controlled with coordinated deployments
- when breaking changes can be done with a full stop-the-world migration

## decision_signals
- need: long-lived event streams with many consumers
- need: adding fields or changing semantics over time
- willing to accept: increases complexity in consumers that must handle multiple versions

## advantages
- enables independent evolution of producers and consumers
- reduces risk during deployments and rollouts

## disadvantages
- increases complexity in consumers that must handle multiple versions
- requires governance to avoid version sprawl

## anti_patterns
- use this when events are internal and tightly controlled with coordinated deployments
- use this when breaking changes can be done with a full stop-the-world migration
- ignoring the downside that increases complexity in consumers that must handle multiple versions

## real_world_examples
- adding optional fields while keeping old consumers ignoring unknown fields
- emitting a new event type order_created_v2 and deprecating v1 gradually

# Event Stream Partitioning

## chunk_id
- 6.20


## category
- messaging_systems

## type
- messaging_pattern

## definition
- distributing an event stream across partitions so throughput scales while preserving ordering within each partition key.

## when_to_use
- scaling high-throughput streams beyond a single consumer or node
- requiring per-entity ordering while allowing parallel processing
- reducing hotspots by spreading keys across partitions

## when_not_to_use
- when strict global ordering is required
- when no stable key exists to keep related events together

## decision_signals
- need: scaling high-throughput streams beyond a single consumer or node
- need: requiring per-entity ordering while allowing parallel processing
- willing to accept: skewed keys can create hot partitions and lag

## advantages
- enables horizontal scale for producers and consumers
- provides a clear model for ordering and concurrency

## disadvantages
- skewed keys can create hot partitions and lag
- changing partition counts can impact ordering and consumer behavior

## anti_patterns
- use this when strict global ordering is required
- use this when no stable key exists to keep related events together
- ignoring the downside that skewed keys can create hot partitions and lag

## real_world_examples
- partitioning by account_id so balance updates are ordered per account
- using consistent hashing on user_id to balance partitions

# Exactly Once Processing Tradeoffs

## chunk_id
- 6.21


## category
- messaging_systems

## type
- messaging_pattern

## definition
- evaluating the cost and complexity of achieving exactly-once effects versus using at-least-once delivery with idempotency.

## when_to_use
- financial or billing workflows where duplicates are unacceptable
- stream processing where state updates must not be applied twice
- auditing requirements that require strict effect semantics

## when_not_to_use
- when idempotency is sufficient and simpler
- when end-to-end exactly-once cannot be guaranteed across external systems

## decision_signals
- need: financial or billing workflows where duplicates are unacceptable
- need: stream processing where state updates must not be applied twice
- willing to accept: often requires tight coupling to platform features and careful configuration

## advantages
- reduces duplicate effects and simplifies some reconciliation
- improves correctness guarantees for sensitive workflows

## disadvantages
- often requires tight coupling to platform features and careful configuration
- can reduce throughput and increase operational risk

## anti_patterns
- use this when idempotency is sufficient and simpler
- use this when end-to-end exactly-once cannot be guaranteed across external systems
- ignoring the downside that often requires tight coupling to platform features and careful configuration

## real_world_examples
- using transactional producers and consumer offsets tied to state commits
- implementing inbox/outbox with unique constraints to enforce once-only effects

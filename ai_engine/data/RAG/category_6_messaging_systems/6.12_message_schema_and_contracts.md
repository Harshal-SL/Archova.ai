# Message Schema And Contracts

## chunk_id
- 6.12


## category
- messaging_systems

## type
- messaging_pattern

## definition
- defining message fields, types, and semantics so producers and consumers can evolve independently without breaking.

## when_to_use
- multiple teams publish and consume shared event types
- long-lived topics where consumers may lag behind deployments
- integrating third-party systems with strict contracts

## when_not_to_use
- when messages are internal and short-lived with a single producer and consumer
- when the system cannot enforce any schema validation in practice

## decision_signals
- need: multiple teams publish and consume shared event types
- need: long-lived topics where consumers may lag behind deployments
- willing to accept: schema governance adds process overhead

## advantages
- reduces breaking changes and accelerates integration
- enables validation, tooling, and documentation automation

## disadvantages
- schema governance adds process overhead
- overly rigid schemas can slow iteration for early-stage products

## anti_patterns
- use this when messages are internal and short-lived with a single producer and consumer
- use this when the system cannot enforce any schema validation in practice
- ignoring the downside that schema governance adds process overhead

## real_world_examples
- defining an order_created schema with required ids and optional enrichment fields
- using versioned event types to manage evolution across services

# Outbox And Transactional Messaging

## chunk_id
- 6.16


## category
- messaging_systems

## type
- messaging_pattern

## definition
- ensuring published messages reflect committed database state by writing events transactionally and relaying them to the broker.

## when_to_use
- preventing lost or phantom events during failures
- integrating state changes with downstream processing reliably
- building event-driven microservices without distributed transactions

## when_not_to_use
- when the broker supports strong transactions across publish and commit and it is acceptable to depend on them
- when integration is synchronous and does not need event durability

## decision_signals
- need: preventing lost or phantom events during failures
- need: integrating state changes with downstream processing reliably
- willing to accept: adds a relay component and operational complexity

## advantages
- improves consistency between state and emitted events
- supports replay and recovery after outages

## disadvantages
- adds a relay component and operational complexity
- consumers still need idempotency because duplicates can occur

## anti_patterns
- use this when the broker supports strong transactions across publish and commit and it is acceptable to depend on them
- use this when integration is synchronous and does not need event durability
- ignoring the downside that adds a relay component and operational complexity

## real_world_examples
- outbox table polled by a relay that publishes to a topic with retries
- transactional writes of events alongside order state updates

# Idempotent Consumers

## chunk_id
- 6.6


## category
- messaging_systems

## type
- messaging_pattern

## definition
- consumer handlers designed so processing the same message multiple times has the same effect as processing it once.

## when_to_use
- at-least-once delivery with retries and redelivery
- side effects like payments, inventory updates, and emails
- processing that can be deduplicated using event ids

## when_not_to_use
- when a system cannot store dedupe state and duplicates are impossible
- when the handler inherently creates unique effects each time

## decision_signals
- need: at-least-once delivery with retries and redelivery
- need: side effects like payments, inventory updates, and emails
- willing to accept: adds state management for deduplication and idempotency keys

## advantages
- makes retries safe and simplifies recovery from crashes
- reduces coupling to broker-specific exactly-once features

## disadvantages
- adds state management for deduplication and idempotency keys
- can be tricky for non-commutative operations and aggregates

## anti_patterns
- use this when a system cannot store dedupe state and duplicates are impossible
- use this when the handler inherently creates unique effects each time
- ignoring the downside that adds state management for deduplication and idempotency keys

## real_world_examples
- deduplicating payment_captured events by event_id in a database table
- using natural keys and upserts so repeated updates do not create duplicates

# Retention And Compaction Policies

## chunk_id
- 6.18


## category
- messaging_systems

## type
- messaging_pattern

## definition
- configuring how long messages are kept and whether streams are compacted to the latest value per key.

## when_to_use
- balancing storage cost with replay and audit needs
- enabling consumers to rebuild projections from a history window
- maintaining latest-state topics using compaction

## when_not_to_use
- when regulatory requirements mandate longer retention than the platform can support
- when compaction would break consumers expecting every intermediate event

## decision_signals
- need: balancing storage cost with replay and audit needs
- need: enabling consumers to rebuild projections from a history window
- willing to accept: retention misconfiguration can cause irrecoverable data loss

## advantages
- controls storage growth and broker resource usage
- supports replay and recovery workflows with defined windows

## disadvantages
- retention misconfiguration can cause irrecoverable data loss
- compaction semantics can be misunderstood and misused

## anti_patterns
- use this when regulatory requirements mandate longer retention than the platform can support
- use this when compaction would break consumers expecting every intermediate event
- ignoring the downside that retention misconfiguration can cause irrecoverable data loss

## real_world_examples
- retaining order events for 14 days for consumer replays
- compacting user_profile topics so new consumers can bootstrap quickly

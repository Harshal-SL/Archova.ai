# Lost Update and Race Condition


## chunk_id
- 11.15

## category
- failure_modes

## type
- failure_mode

## definition
- concurrent operations overwrite each other or observe stale state, causing updates to be lost or invariants to be violated.

## when_to_use
- systems with concurrent writes to the same entity
- inventory, counters, and idempotency handling
- diagnosing intermittent correctness bugs under load

## when_not_to_use
- append-only event logs where state is derived deterministically
- single-threaded systems with no concurrency

## decision_signals
- need: systems with concurrent writes to the same entity
- need: inventory, counters, and idempotency handling
- willing to accept: can silently corrupt business logic outcomes

## advantages
- motivates optimistic concurrency control and atomic operations
- improves correctness under parallelism

## disadvantages
- can silently corrupt business logic outcomes
- hard to reproduce without concurrency testing

## anti_patterns
- using this when append-only event logs where state is derived deterministically
- using this when single-threaded systems with no concurrency
- ignoring the downside that can silently corrupt business logic outcomes

## real_world_examples
- two checkout requests decrement inventory from the same starting value
- profile updates overwrite each other because last write wins

# Deadlock and Lock Contention


## chunk_id
- 11.16

## category
- failure_modes

## type
- failure_mode

## definition
- transactions or threads block each other due to lock ordering issues or excessive contention, causing throughput collapse and timeouts.

## when_to_use
- relational databases and systems with explicit locks
- diagnosing sudden latency spikes and low throughput under load
- designing transaction boundaries and lock ordering

## when_not_to_use
- lock-free append-only systems with minimal shared mutable state
- workloads with no concurrency and no transactional locking

## decision_signals
- need: relational databases and systems with explicit locks
- need: diagnosing sudden latency spikes and low throughput under load
- willing to accept: can cause widespread timeouts and retries

## advantages
- motivates smaller transactions and consistent lock ordering
- improves performance through contention reduction

## disadvantages
- can cause widespread timeouts and retries
- can be intermittent and dependent on traffic shape

## anti_patterns
- using this when lock-free append-only systems with minimal shared mutable state
- using this when workloads with no concurrency and no transactional locking
- ignoring the downside that can cause widespread timeouts and retries

## real_world_examples
- two transactions lock rows in opposite order and deadlock
- hot row updates cause lock waits and queue up requests

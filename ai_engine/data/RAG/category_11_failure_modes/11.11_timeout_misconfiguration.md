# Timeout Misconfiguration


## chunk_id
- 11.11

## category
- failure_modes

## type
- failure_mode

## definition
- incorrect timeout settings (too long, too short, inconsistent across hops) that cause stuck resources, premature failures, or retry amplification.

## when_to_use
- systems with multiple network hops and downstream dependencies
- debugging hanging requests, pool exhaustion, or unexpected cancellations
- designing layered timeouts and budgets

## when_not_to_use
- single-process systems with no network calls
- workloads that are strictly asynchronous with durable queues

## decision_signals
- need: systems with multiple network hops and downstream dependencies
- need: debugging hanging requests, pool exhaustion, or unexpected cancellations
- willing to accept: misaligned timeouts can cause cascading failures and retry storms

## advantages
- encourages end-to-end latency budgeting and predictable failure behavior
- reduces tail latency and prevents resource starvation

## disadvantages
- misaligned timeouts can cause cascading failures and retry storms
- hard to tune without traffic patterns and observability

## anti_patterns
- using this when single-process systems with no network calls
- using this when workloads that are strictly asynchronous with durable queues
- ignoring the downside that misaligned timeouts can cause cascading failures and retry storms

## real_world_examples
- client timeout is 2s but server waits 30s on dependency, exhausting threads
- retries occur because upstream timeout is shorter than downstream p99 latency

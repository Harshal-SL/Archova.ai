# Cache Partitioning by Tenant


## chunk_id
- 4.15

## category
- caching_strategies

## type
- caching_strategy

## definition
- isolating cache usage by tenant using namespaces, quotas, and shard allocation to prevent noisy neighbors.

## when_to_use
- multi-tenant saas where tenants have uneven traffic and data sizes
- preventing one tenant from evicting others from shared caches
- enforcing per-tenant privacy and access boundaries

## when_not_to_use
- single-tenant systems or dedicated caches per tenant
- when tenant identity is not reliably available at cache access points

## decision_signals
- need: multi-tenant saas where tenants have uneven traffic and data sizes
- need: preventing one tenant from evicting others from shared caches
- willing to accept: increases complexity in key design and capacity management

## advantages
- improves fairness and reduces cross-tenant interference
- simplifies auditing and incident response per tenant

## disadvantages
- increases complexity in key design and capacity management
- can reduce overall cache utilization if partitions are too rigid

## anti_patterns
- using this when single-tenant systems or dedicated caches per tenant
- use this when tenant identity is not reliably available at cache access points
- ignoring the downside that increases complexity in key design and capacity management

## real_world_examples
- per-tenant key prefixes plus per-tenant memory quotas
- tenant-aware cache sharding for large enterprise customers

# Cache Key Design


## chunk_id
- 4.6

## category
- caching_strategies

## type
- caching_strategy

## definition
- designing stable cache keys and namespaces so cached entries are correct, isolatable, and easy to invalidate.

## when_to_use
- any cache storing user, tenant, or variant-specific data
- multi-layer caching where keys must align across tiers
- preventing collisions and supporting targeted invalidation

## when_not_to_use
- when keys depend on unstable serialization or unordered fields
- when key cardinality would explode cache size without bounds

## decision_signals
- need: any cache storing user, tenant, or variant-specific data
- need: multi-layer caching where keys must align across tiers
- willing to accept: requires careful versioning as schemas and response shapes change

## advantages
- reduces correctness bugs from key collisions and wrong variants
- enables precise invalidation and better hit rates

## disadvantages
- requires careful versioning as schemas and response shapes change
- poor keys can create hotspots or extreme cardinality

## anti_patterns
- use this when keys depend on unstable serialization or unordered fields
- use this when key cardinality would explode cache size without bounds
- ignoring the downside that requires careful versioning as schemas and response shapes change

## real_world_examples
- namespacing keys by tenant and entity version
- including locale and feature variant in content keys

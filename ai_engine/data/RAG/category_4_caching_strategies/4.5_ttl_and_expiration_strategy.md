# TTL and Expiration Strategy


## chunk_id
- 4.5

## category
- caching_strategies

## type
- caching_strategy

## definition
- choosing ttl, eviction, and refresh rules that balance freshness, hit rate, and cost.

## when_to_use
- caches where data freshness requirements vary by entity type
- preventing unbounded growth and controlling memory usage
- coordinating cache behavior across layers like cdn and app cache

## when_not_to_use
- when strict freshness is required but no invalidation signal exists
- when ttl values are chosen arbitrarily without measurement

## decision_signals
- need: caches where data freshness requirements vary by entity type
- need: preventing unbounded growth and controlling memory usage
- willing to accept: wrong ttl can increase stale reads or reduce hit rate

## advantages
- bounds staleness and controls cache size
- improves predictability of cache behavior and load on origins

## disadvantages
- wrong ttl can increase stale reads or reduce hit rate
- synchronized expirations can cause stampedes without jitter

## anti_patterns
- use this when strict freshness is required but no invalidation signal exists
- use this when ttl values are chosen arbitrarily without measurement
- ignoring the downside that wrong ttl can increase stale reads or reduce hit rate

## real_world_examples
- shorter ttl for inventory counts and longer ttl for static product metadata
- adding ttl jitter to avoid synchronized expiry bursts

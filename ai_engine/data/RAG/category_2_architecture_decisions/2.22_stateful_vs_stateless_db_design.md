# Stateful vs Stateless DB Design


## chunk_id
- 2.22

## category
- architecture_decisions

## type
- decision

## definition
- a state modeling decision between mutable current-state tables and immutable event logs with derived read models.

## when_to_use
- mutable state tables for simple oltp systems and crud
- event log models for auditability and replay requirements
- derived views when read models differ from write intent

## when_not_to_use
- event log designs for small systems without audit needs
- mutable-only designs when you need full history and replay

## decision_signals
- need: mutable state tables for simple oltp systems and crud
- need: event log models for auditability and replay requirements
- willing to accept: mutable state loses history without extra audit mechanisms

## advantages
- mutable state is simple and query-friendly for current state
- event logs provide complete history and deterministic rebuilds

## disadvantages
- mutable state loses history without extra audit mechanisms
- event log designs add complexity in projections and consistency

## anti_patterns
- using this when event log designs for small systems without audit needs
- using this when mutable-only designs when you need full history and replay
- ignoring the downside that mutable state loses history without extra audit mechanisms

## real_world_examples
- relational oltp with current-state rows (mutable)
- event store plus projections for aggregates (event log)

# Push vs Pull Architecture


## chunk_id
- 2.13

## category
- architecture_decisions

## type
- decision

## definition
- a delivery model choice where producers push updates to consumers or consumers pull work/data on demand.

## when_to_use
- push for realtime notifications and webhooks
- pull for work queues and controlled consumption
- pull for backpressure and consumer-driven scaling

## when_not_to_use
- push when consumers are unreliable or cannot accept bursts
- pull when low-latency updates are required

## decision_signals
- need: push for realtime notifications and webhooks
- need: pull for work queues and controlled consumption
- willing to accept: push requires retry, dedup, and rate limiting controls

## advantages
- push achieves low latency for user-facing updates
- pull enables stable throughput and consumer backpressure

## disadvantages
- push requires retry, dedup, and rate limiting controls
- pull can introduce staleness and polling overhead

## anti_patterns
- using this when push when consumers are unreliable or cannot accept bursts
- using this when pull when low-latency updates are required
- ignoring the downside that push requires retry, dedup, and rate limiting controls

## real_world_examples
- webhook event delivery to third parties (push)
- kafka consumer groups processing logs (pull)

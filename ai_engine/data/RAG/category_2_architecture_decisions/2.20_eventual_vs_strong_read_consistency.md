# Eventual vs Strong Read Consistency


## chunk_id
- 2.20

## category
- architecture_decisions

## type
- decision

## definition
- a read-model decision between accepting stale reads (eventual) and requiring up-to-date reads (strong).

## when_to_use
- strong reads for balances, permissions, and inventory gates
- eventual reads for feeds, search results, and analytics dashboards
- session consistency to guarantee read-your-writes for user actions

## when_not_to_use
- eventual reads when stale data causes incorrect transactions
- strong reads when geo-latency and availability are top priorities

## decision_signals
- need: strong reads for balances, permissions, and inventory gates
- need: eventual reads for feeds, search results, and analytics dashboards
- willing to accept: strong reads can increase tail latency under replication

## advantages
- strong reads reduce correctness bugs and user confusion
- eventual reads improve availability and reduce replication latency

## disadvantages
- strong reads can increase tail latency under replication
- eventual reads require conflict handling and ux mitigation

## anti_patterns
- using this when eventual reads when stale data causes incorrect transactions
- using this when strong reads when geo-latency and availability are top priorities
- ignoring the downside that strong reads can increase tail latency under replication

## real_world_examples
- account balance reads from leader replicas (strong)
- timeline reads from cached replicas (eventual)

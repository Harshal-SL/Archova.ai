# Idempotency Design Rules


## chunk_id
- 2.8

## category
- architecture_decisions

## type
- decision

## definition
- a set of api rules ensuring retries and duplicate requests do not create duplicate side effects.

## when_to_use
- payment and order creation endpoints with client retries
- distributed workflows with at-least-once delivery
- network failure handling with automatic retries

## when_not_to_use
- write operations without a stable idempotency key
- processes where duplicates cannot be detected or reversed

## decision_signals
- need: payment and order creation endpoints with client retries
- need: distributed workflows with at-least-once delivery
- willing to accept: requires dedup storage and retention policies

## advantages
- enables safe retries and improves reliability
- reduces duplicate charges and duplicate state transitions

## disadvantages
- requires dedup storage and retention policies
- adds complexity to write paths and auditing

## anti_patterns
- using this when write operations without a stable idempotency key
- using this when processes where duplicates cannot be detected or reversed
- ignoring the downside that requires dedup storage and retention policies

## real_world_examples
- stripe idempotency keys for charge creation
- deduplicated message processing in kafka consumers

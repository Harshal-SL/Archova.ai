# CAP Theorem Architecture Implications


## chunk_id
- 2.4

## category
- architecture_decisions

## type
- decision

## definition
- a distributed system rule that under network partitions you must trade off consistency and availability.

## when_to_use
- multi-region systems where partitions are expected
- distributed databases and replicated state machines
- sli and slo design for critical data paths

## when_not_to_use
- single-node or non-replicated systems without partitions
- as a blanket rule without domain-specific correctness needs

## decision_signals
- need: multi-region systems where partitions are expected
- need: distributed databases and replicated state machines
- willing to accept: can be oversimplified and misapplied

## advantages
- forces explicit design choices for failure modes
- improves alignment between data guarantees and slos

## disadvantages
- can be oversimplified and misapplied
- does not capture latency and throughput tradeoffs directly

## anti_patterns
- using this when single-node or non-replicated systems without partitions
- using this when as a blanket rule without domain-specific correctness needs
- ignoring the downside that can be oversimplified and misapplied

## real_world_examples
- etcd and zookeeper favor consistency over availability
- cassandra favors availability with eventual consistency

# Vertical vs Horizontal Scaling Decision


## chunk_id
- 2.14

## category
- architecture_decisions

## type
- decision

## definition
- a decision framework for choosing scale-up versus scale-out based on throughput goals, failure tolerance, cost profile, and operational complexity.

## when_to_use
- vertical scaling for quick wins on single-node bottlenecks
- horizontal scaling for stateless services and high availability
- horizontal scaling when load can be partitioned or replicated

## when_not_to_use
- vertical scaling when hardware limits and downtime risk are high
- horizontal scaling for stateful workloads without sharding strategy

## decision_signals
- need: vertical scaling for quick wins on single-node bottlenecks
- need: horizontal scaling for stateless services and high availability
- willing to accept: vertical scaling has hard limits and can increase blast radius

## advantages
- vertical scaling is simple and keeps architecture unchanged
- horizontal scaling improves resilience and throughput

## disadvantages
- vertical scaling has hard limits and can increase blast radius
- horizontal scaling adds coordination, routing, and consistency complexity

## anti_patterns
- using this for vertical scaling when hardware limits and downtime risk are high
- using this for horizontal scaling of stateful workloads without a sharding strategy
- ignoring the downside that vertical scaling has hard limits and can increase blast radius

## real_world_examples
- upgrading a database instance size (vertical)
- adding more api replicas behind a load balancer (horizontal)

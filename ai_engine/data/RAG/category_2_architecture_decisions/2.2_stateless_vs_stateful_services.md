# Stateless vs Stateful Services


## chunk_id
- 2.2

## category
- architecture_decisions

## type
- decision

## definition
- a service design choice between keeping no server-side session (stateless) or retaining in-memory/session state (stateful).

## when_to_use
- stateless services for horizontal scaling and autoscaling
- stateful services for low-latency in-memory coordination
- stateless services for serverless and container orchestration

## when_not_to_use
- stateful services when failover and scaling must be simple
- stateless services when state cannot be externalized reliably

## decision_signals
- need: stateless services for horizontal scaling and autoscaling
- need: stateful services for low-latency in-memory coordination
- willing to accept: stateless services require external state stores and caching

## advantages
- stateless services enable easy scaling and blue/green rollout
- stateful services can reduce latency for live session workflows

## disadvantages
- stateless services require external state stores and caching
- stateful services complicate sharding, failover, and deployment

## anti_patterns
- using this when stateful services when failover and scaling must be simple
- using this when stateless services when state cannot be externalized reliably
- ignoring the downside that stateless services require external state stores and caching

## real_world_examples
- stateless rest api tiers behind a load balancer
- stateful realtime game room servers

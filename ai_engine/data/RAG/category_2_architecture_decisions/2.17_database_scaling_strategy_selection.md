# Database Scaling Strategy Selection


## chunk_id
- 2.17

## category
- architecture_decisions

## type
- decision

## definition
- a decision guide for choosing replication, partitioning, or sharding to scale a database based on workload and data size.

## when_to_use
- read replicas for read-heavy workloads and low write contention
- sharding for large datasets and high write throughput
- partitioning for time-based retention and query pruning

## when_not_to_use
- before indexing and schema optimization are exhausted
- when operational complexity cannot be supported

## decision_signals
- need: read replicas for read-heavy workloads and low write contention
- need: sharding for large datasets and high write throughput
- willing to accept: increases operational burden and failure modes

## advantages
- enables scaling beyond a single node and improves availability
- aligns storage topology with access patterns and slos

## disadvantages
- increases operational burden and failure modes
- complicates queries, transactions, and consistency

## anti_patterns
- using this when before indexing and schema optimization are exhausted
- use this when operational complexity cannot be supported
- ignoring the downside that increases operational burden and failure modes

## real_world_examples
- read replicas for product catalog reads
- sharded user tables for high-scale multi-tenant systems

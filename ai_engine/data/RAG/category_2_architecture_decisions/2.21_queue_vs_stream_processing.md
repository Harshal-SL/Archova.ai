# Queue vs Stream Processing


## chunk_id
- 2.21

## category
- architecture_decisions

## type
- decision

## definition
- a messaging decision between work-queue semantics and append-only stream semantics with replay.

## when_to_use
- queues for task distribution and competing workers
- streams for ordered event logs and replayable processing
- streams for analytics pipelines and audit requirements

## when_not_to_use
- queues when consumers need reprocessing and backfills
- streams when you only need simple point-to-point tasks

## decision_signals
- need: queues for task distribution and competing workers
- need: streams for ordered event logs and replayable processing
- willing to accept: queues provide limited replay and weak historical introspection

## advantages
- queues are simple for load leveling and work distribution
- streams enable replay, multiple consumers, and time travel

## disadvantages
- queues provide limited replay and weak historical introspection
- streams require partitioning strategy and consumer lag handling

## anti_patterns
- using this when queues when consumers need reprocessing and backfills
- using this when streams when you only need simple point-to-point tasks
- ignoring the downside that queues provide limited replay and weak historical introspection

## real_world_examples
- rabbitmq or sqs for background jobs
- kafka for event streaming and analytics

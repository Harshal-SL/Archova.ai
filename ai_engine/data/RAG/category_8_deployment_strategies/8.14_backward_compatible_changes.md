# Backward Compatible Changes


## chunk_id
- 8.14

## category
- deployment_strategies

## type
- deployment_strategy

## definition
- making changes that old clients and old service versions can still work with during mixed-version deployments.

## when_to_use
- rolling deploys and canary releases where versions overlap
- schema migrations that require phased rollout
- public apis with long-lived clients

## when_not_to_use
- when a breaking change is unavoidable and a coordinated cutover is possible
- when supporting backward compatibility would create unacceptable complexity

## decision_signals
- need: rolling deploys and canary releases where versions overlap
- need: schema migrations that require phased rollout
- willing to accept: can delay cleanup of old behavior and increase tech debt

## advantages
- reduces deployment risk in distributed systems
- enables gradual rollouts with safer rollback options

## disadvantages
- can delay cleanup of old behavior and increase tech debt
- requires careful contract design and testing

## anti_patterns
- use this when a breaking change is unavoidable and a coordinated cutover is possible
- use this when supporting backward compatibility would create unacceptable complexity
- ignoring the downside that can delay cleanup of old behavior and increase tech debt

## real_world_examples
- adding optional fields and never changing existing semantics
- supporting dual-read logic during a phased migration

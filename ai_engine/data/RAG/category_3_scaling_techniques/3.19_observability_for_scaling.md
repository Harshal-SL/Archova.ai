# Observability For Scaling

## chunk_id
- 3.19


## category
- scaling_techniques

## type
- scaling_technique

## definition
- using metrics, logs, and traces to understand saturation, bottlenecks, and capacity so scaling actions are data-driven.

## when_to_use
- diagnosing latency spikes and throughput ceilings
- validating whether scaling changes improved slos
- detecting hotspots, retries, and queue buildup early

## when_not_to_use
- when instrumentation overhead is unacceptable for an early prototype
- when teams cannot maintain dashboards, alerts, and runbooks

## decision_signals
- need: diagnosing latency spikes and throughput ceilings
- need: validating whether scaling changes improved slos
- willing to accept: requires consistent instrumentation and ongoing maintenance

## advantages
- reduces guesswork and speeds up incident response
- supports automated scaling based on reliable signals

## disadvantages
- requires consistent instrumentation and ongoing maintenance
- can create noise if signals and alerts are not curated

## anti_patterns
- use this when instrumentation overhead is unacceptable for an early prototype
- use this when teams cannot maintain dashboards, alerts, and runbooks
- ignoring the downside that requires consistent instrumentation and ongoing maintenance

## real_world_examples
- dashboards for cpu, queue depth, p95 latency, and error rate
- tracing to identify the slowest downstream dependency in a request path

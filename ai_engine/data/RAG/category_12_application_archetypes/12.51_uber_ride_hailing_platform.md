# Uber Ride Hailing Platform

## chunk_id
- 12.51


## category

## type
- application_archetype

## definition
- a real-time marketplace that matches riders and drivers using geo partitioning, low-latency dispatch, and event-driven trip state.

## when_to_use
- building real-time matching with geo updates and strict latency budgets
- designing state machines for trip lifecycle with cancellations and retries
- scaling bursty demand with regional isolation and rate limits

## when_not_to_use
- offline scheduling or batch assignment where latency is not user-visible
- small regional systems where a single database can handle dispatch

## decision_signals
- end-to-end dispatch latency target (<300ms) for matching decisions
- high write rate for location events (>1k updates/s per region)
- partitioning by region/cell required to avoid hotspots

## advantages
- clear event model for trip lifecycle and pricing decisions
- strong use of partitioning and backpressure for write-heavy streams

## disadvantages
- out-of-order and duplicate events are common and must be handled
- peak events can trigger retry storms without strict caps

## anti_patterns
- treating location updates as transactional records instead of streams
- global cross-region matching that ignores latency and availability zones
- unbounded fan-out to all drivers without filtering and throttling

# Data Quality Constraints and Validation


## chunk_id
- 5.25

## category
- database_design

## type
- data_pattern

## definition
- enforcing correctness using constraints, validation rules, and application checks to prevent bad data from entering the system.

## when_to_use
- preventing invalid states that are costly to clean up later
- protecting analytics and downstream pipelines from corrupt inputs
- enforcing tenant boundaries and required fields

## when_not_to_use
- when constraints would block legitimate partial writes during staged workflows
- when validation must be flexible and better handled at the application boundary

## decision_signals
- need: preventing invalid states that are costly to clean up later
- need: protecting analytics and downstream pipelines from corrupt inputs
- willing to accept: overly strict rules can reduce agility and cause write failures

## advantages
- reduces operational toil caused by bad data
- makes invariants explicit and testable

## disadvantages
- overly strict rules can reduce agility and cause write failures
- validation logic can drift between database and services if duplicated

## anti_patterns
- use this when constraints would block legitimate partial writes during staged workflows
- use this when validation must be flexible and better handled at the application boundary
- ignoring the downside that overly strict rules can reduce agility and cause write failures

## real_world_examples
- enforcing uniqueness on (tenant_id, external_id) to prevent duplicates
- validating status transitions to block impossible workflow states

# Optimistic Concurrency Control


## chunk_id
- 5.8

## category
- database_design

## type
- data_pattern

## definition
- preventing lost updates by detecting write conflicts using versions, etags, or compare-and-swap semantics.

## when_to_use
- high read concurrency with relatively rare write conflicts
- APIs that support conditional updates (if-match)
- systems where locking would reduce throughput too much

## when_not_to_use
- hot records with frequent conflicting writes
- workflows that require strict ordering across many updates

## decision_signals
- need: high read concurrency with relatively rare write conflicts
- need: aPIs that support conditional updates (if-match)
- willing to accept: clients must handle retries and conflict resolution

## advantages
- avoids locks and improves throughput under low contention
- makes conflicts explicit and recoverable

## disadvantages
- clients must handle retries and conflict resolution
- conflict storms can cause repeated failures during spikes

## anti_patterns
- using this when hot records with frequent conflicting writes
- using this when workflows that require strict ordering across many updates
- ignoring the downside that clients must handle retries and conflict resolution

## real_world_examples
- updating a shopping cart with a version field to prevent overwrites
- using etags to protect profile edits from racing updates

# Schema Migrations and Versioning


## chunk_id
- 5.18

## category
- database_design

## type
- data_pattern

## definition
- evolving schemas safely using backward-compatible changes, versioned fields, and controlled rollout and backfill.

## when_to_use
- deploying new fields or tables while keeping old readers working
- handling large datasets where one-shot migrations are risky
- coordinating schema changes across multiple services

## when_not_to_use
- when a breaking change is unavoidable and a full outage window is approved
- when the database is disposable and can be rebuilt from source data

## decision_signals
- need: deploying new fields or tables while keeping old readers working
- need: handling large datasets where one-shot migrations are risky
- willing to accept: requires discipline in compatibility and cleanup of old fields

## advantages
- reduces downtime risk by rolling changes out gradually
- supports continuous delivery without schema lockstep

## disadvantages
- requires discipline in compatibility and cleanup of old fields
- backfills can be expensive and operationally risky

## anti_patterns
- use this when a breaking change is unavoidable and a full outage window is approved
- use this when the database is disposable and can be rebuilt from source data
- ignoring the downside that requires discipline in compatibility and cleanup of old fields

## real_world_examples
- adding a nullable column, updating writers, then backfilling in batches
- using a version field to support dual-read logic during migrations

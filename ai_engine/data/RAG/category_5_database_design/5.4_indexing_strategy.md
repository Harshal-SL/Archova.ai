# Indexing Strategy


## chunk_id
- 5.4

## category
- database_design

## type
- data_pattern

## definition
- designing indexes to match query filters and sorts while controlling write overhead and storage cost.

## when_to_use
- establishing performance baselines for critical queries
- supporting new endpoints that add filter/sort requirements
- reducing full scans on large datasets

## when_not_to_use
- when the dataset is small and performance is already acceptable
- when the query pattern is unstable and likely to change soon

## decision_signals
- need: establishing performance baselines for critical queries
- need: supporting new endpoints that add filter/sort requirements
- willing to accept: increases write latency and storage consumption

## advantages
- speeds up reads and can enable efficient pagination
- reduces load on compute and storage by avoiding scans

## disadvantages
- increases write latency and storage consumption
- too many indexes can slow bulk loads and maintenance

## anti_patterns
- use this when the dataset is small and performance is already acceptable
- use this when the query pattern is unstable and likely to change soon
- ignoring the downside that increases write latency and storage consumption

## real_world_examples
- adding a compound index on (tenant_id, created_at) for tenant-scoped timelines
- using partial indexes to accelerate only active records

# Materialized Views


## chunk_id
- 5.15

## category
- database_design

## type
- data_pattern

## definition
- storing precomputed query results to speed up reads, refreshed on a schedule or by change events.

## when_to_use
- expensive joins and aggregates that are read frequently
- reporting and analytics queries that can tolerate some staleness
- workloads where the read model differs from the write model

## when_not_to_use
- when the view must be perfectly fresh at all times
- when refresh cost exceeds the benefit or introduces fragile pipelines

## decision_signals
- need: expensive joins and aggregates that are read frequently
- need: reporting and analytics queries that can tolerate some staleness
- willing to accept: introduces staleness and refresh logic

## advantages
- significantly reduces query latency for complex reads
- isolates read performance from write schema complexity

## disadvantages
- introduces staleness and refresh logic
- requires careful backfill and failure recovery for refresh jobs

## anti_patterns
- use this when the view must be perfectly fresh at all times
- use this when refresh cost exceeds the benefit or introduces fragile pipelines
- ignoring the downside that introduces staleness and refresh logic

## real_world_examples
- precomputing daily revenue by region for dashboards
- maintaining a denormalized user profile summary for fast api responses

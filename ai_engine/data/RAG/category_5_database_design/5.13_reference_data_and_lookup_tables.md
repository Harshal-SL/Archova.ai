# Reference Data and Lookup Tables


## chunk_id
- 5.13

## category
- database_design

## type
- data_pattern

## definition
- storing slowly changing shared values (countries, tax rates, feature catalogs) in authoritative tables or collections.

## when_to_use
- multiple services or modules need consistent enumerations
- validation requires a controlled set of values
- reference data is updated occasionally but read frequently

## when_not_to_use
- when the value set is tiny and truly static (code constants are fine)
- when reference data is tenant-specific and should not be global

## decision_signals
- need: multiple services or modules need consistent enumerations
- need: validation requires a controlled set of values
- willing to accept: adds joins or extra reads if not cached

## advantages
- centralizes updates and reduces duplicated logic
- enables audits and effective dating (valid_from, valid_to)

## disadvantages
- adds joins or extra reads if not cached
- requires governance for who can change reference data

## anti_patterns
- use this when the value set is tiny and truly static (code constants are fine)
- use this when reference data is tenant-specific and should not be global
- ignoring the downside that adds joins or extra reads if not cached

## real_world_examples
- a tax_rate table keyed by (country, effective_date)
- a currency table with minor unit and symbol metadata

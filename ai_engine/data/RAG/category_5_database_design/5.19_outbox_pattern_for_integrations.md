# Outbox Pattern for Integrations


## chunk_id
- 5.19

## category
- database_design

## type
- data_pattern

## definition
- recording integration events in the same database transaction as state changes, then publishing them asynchronously.

## when_to_use
- avoiding lost events between database commits and message publishing
- integrating microservices with reliable event delivery
- enabling replay and recovery of published events

## when_not_to_use
- when synchronous integration is required and failure handling is simple
- when the system cannot tolerate eventual publication delays

## decision_signals
- need: avoiding lost events between database commits and message publishing
- need: integrating microservices with reliable event delivery
- willing to accept: requires a relay process and outbox cleanup

## advantages
- improves consistency between stored state and emitted events
- supports retries and at-least-once delivery to messaging systems

## disadvantages
- requires a relay process and outbox cleanup
- consumers must be idempotent because duplicates can happen

## anti_patterns
- use this when synchronous integration is required and failure handling is simple
- use this when the system cannot tolerate eventual publication delays
- ignoring the downside that requires a relay process and outbox cleanup

## real_world_examples
- writing an order_created event to an outbox table and publishing to a broker
- emitting customer_updated events after committing profile changes

# Data Retention and TTL


## chunk_id
- 5.17

## category
- database_design

## type
- data_pattern

## definition
- defining how long data is kept and automating expiry and archival using ttl, partition drops, or lifecycle rules.

## when_to_use
- controlling storage costs for logs, telemetry, and transient data
- meeting compliance requirements for deletion and retention windows
- simplifying operational cleanup of stale records

## when_not_to_use
- when legal holds require selective retention overrides not supported by ttl
- when downstream systems depend on historical data without an archive plan

## decision_signals
- need: controlling storage costs for logs, telemetry, and transient data
- need: meeting compliance requirements for deletion and retention windows
- willing to accept: accidental expiry can cause data loss if misconfigured

## advantages
- reduces long-term storage growth and maintenance effort
- improves performance by keeping working sets smaller

## disadvantages
- accidental expiry can cause data loss if misconfigured
- archives and restores can be slow without tested procedures

## anti_patterns
- use this when legal holds require selective retention overrides not supported by ttl
- use this when downstream systems depend on historical data without an archive plan
- ignoring the downside that accidental expiry can cause data loss if misconfigured

## real_world_examples
- expiring password reset tokens after 15 minutes
- retaining detailed logs for 30 days and daily aggregates for 1 year

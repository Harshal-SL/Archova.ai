# Eventual Consistency Read Models


## chunk_id
- 5.16

## category
- database_design

## type
- data_pattern

## definition
- maintaining separate read-optimized projections that update asynchronously from the write source of truth.

## when_to_use
- high-read workloads where a normalized write model is too slow to query
- distributed systems where cross-service joins are impractical
- building search indexes or feed timelines from events

## when_not_to_use
- when user workflows require read-your-writes consistency everywhere
- when projection lag would break business invariants

## decision_signals
- need: high-read workloads where a normalized write model is too slow to query
- need: distributed systems where cross-service joins are impractical
- willing to accept: introduces lag, replay, and reprocessing complexity

## advantages
- scales reads independently from writes
- enables specialized storage per read use case

## disadvantages
- introduces lag, replay, and reprocessing complexity
- requires idempotency and ordering considerations for projection updates

## anti_patterns
- use this when user workflows require read-your-writes consistency everywhere
- use this when projection lag would break business invariants
- ignoring the downside that introduces lag, replay, and reprocessing complexity

## real_world_examples
- projecting order events into a searchable order_summary table
- building a product search index from catalog change events

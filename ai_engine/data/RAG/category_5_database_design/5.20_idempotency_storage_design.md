# Idempotency Storage Design


## chunk_id
- 5.20

## category
- database_design

## type
- data_pattern

## definition
- designing storage structures and constraints that guarantee the same request key produces one logical effect across retries and duplicates.

## when_to_use
- payment, order, or provisioning APIs that clients retry
- event consumers with at-least-once delivery semantics
- workflows where duplicate side effects are unacceptable

## when_not_to_use
- read-only operations without side effects
- low-value actions where duplicate handling overhead is unnecessary

## decision_signals
- need: payment, order, or provisioning APIs that clients retry
- need: event consumers with at-least-once delivery semantics
- willing to accept: additional storage, indexing, and retention management

## advantages
- prevents duplicate side effects with deterministic behavior
- improves auditability of retry outcomes

## disadvantages
- additional storage, indexing, and retention management
- key design mistakes can create hotspots and lock contention

## anti_patterns
- using random dedupe keys that change per retry
- storing idempotency state without expiration or archival
- separating idempotency write from business commit

## real_world_examples
- unique constraint on (tenant_id, idempotency_key) for payment capture
- inbox table keyed by (consumer_group, message_id)

# Data Modeling Fundamentals


## chunk_id
- 5.1

## category
- database_design

## type
- data_pattern

## definition
- choosing entities, relationships, and constraints so the database matches domain needs and access patterns.

## when_to_use
- starting a new system or adding a new bounded context
- redesigning a schema that causes performance or correctness problems
- aligning storage with query patterns and lifecycle requirements

## when_not_to_use
- when the schema is stable and the main bottleneck is compute or network
- when premature optimization would overfit to uncertain queries

## decision_signals
- need: starting a new system or adding a new bounded context
- need: redesigning a schema that causes performance or correctness problems
- willing to accept: requires stakeholder alignment and up-front discovery

## advantages
- reduces rework by making tradeoffs explicit early
- improves performance and correctness by matching real access patterns

## disadvantages
- requires stakeholder alignment and up-front discovery
- mistakes can be costly to unwind once data is large

## anti_patterns
- use this when the schema is stable and the main bottleneck is compute or network
- use this when premature optimization would overfit to uncertain queries
- ignoring the downside that requires stakeholder alignment and up-front discovery

## real_world_examples
- modeling orders and line items to support both checkout and reporting queries
- separating immutable event history from mutable current state

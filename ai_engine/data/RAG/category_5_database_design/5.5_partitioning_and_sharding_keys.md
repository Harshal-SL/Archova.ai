# Partitioning and Sharding Keys


## chunk_id
- 5.5

## category
- database_design

## type
- data_pattern

## definition
- choosing a partition key so data distribution, locality, and query routing scale without hotspots.

## when_to_use
- anticipating growth beyond a single node
- needing tenant isolation or geo locality for latency
- avoiding single-shard write saturation

## when_not_to_use
- when the workload is small and operational overhead would dominate
- when no stable key can distribute writes and match query shapes

## decision_signals
- need: anticipating growth beyond a single node
- need: needing tenant isolation or geo locality for latency
- willing to accept: poor key choice leads to hot partitions and re-sharding pain

## advantages
- enables horizontal scaling of storage and throughput
- improves performance by keeping related data co-located

## disadvantages
- poor key choice leads to hot partitions and re-sharding pain
- cross-partition queries can be slower and more complex

## anti_patterns
- use this when the workload is small and operational overhead would dominate
- use this when no stable key can distribute writes and match query shapes
- ignoring the downside that poor key choice leads to hot partitions and re-sharding pain

## real_world_examples
- partitioning by tenant_id for multi-tenant isolation
- partitioning by (region, user_id_hash) to balance locality and distribution

# Transactions and Consistency


## chunk_id
- 5.7

## category
- database_design

## type
- data_pattern

## definition
- choosing isolation levels and consistency guarantees so multi-step updates remain correct under concurrency.

## when_to_use
- workflows requiring atomic updates across multiple records
- preventing invariants from breaking under concurrent writes
- coordinating state changes that must be all-or-nothing

## when_not_to_use
- when the system can accept eventual consistency with compensations
- when long transactions would create contention and timeouts

## decision_signals
- need: workflows requiring atomic updates across multiple records
- need: preventing invariants from breaking under concurrent writes
- willing to accept: can reduce throughput due to locking or coordination

## advantages
- simplifies correctness by enforcing invariants atomically
- reduces edge cases from partial updates

## disadvantages
- can reduce throughput due to locking or coordination
- distributed transactions are complex and can fail in non-obvious ways

## anti_patterns
- use this when the system can accept eventual consistency with compensations
- use this when long transactions would create contention and timeouts
- ignoring the downside that can reduce throughput due to locking or coordination

## real_world_examples
- reserving inventory and creating an order in a single transaction
- using transactional outbox writes to ensure messages match committed state

# Normalization vs Denormalization


## chunk_id
- 5.2

## category
- database_design

## type
- data_pattern

## definition
- balancing normalized schemas that reduce duplication with denormalized schemas that optimize reads by duplicating data.

## when_to_use
- deciding between join-heavy queries and duplication for read latency
- designing schemas for high-read or high-write workloads
- handling distributed systems where cross-entity joins are expensive

## when_not_to_use
- when requirements are unclear and either choice would be speculative
- when duplication would create correctness risk without a sync mechanism

## decision_signals
- need: deciding between join-heavy queries and duplication for read latency
- need: designing schemas for high-read or high-write workloads
- willing to accept: normalization can require expensive joins at scale

## advantages
- normalization reduces update anomalies and keeps data consistent
- denormalization can reduce query latency and simplify read paths

## disadvantages
- normalization can require expensive joins at scale
- denormalization requires careful update propagation and conflict handling

## anti_patterns
- use this when requirements are unclear and either choice would be speculative
- use this when duplication would create correctness risk without a sync mechanism
- ignoring the downside that normalization can require expensive joins at scale

## real_world_examples
- duplicating product name into order items to keep invoices stable over time
- normalizing user accounts to centralize authentication state updates

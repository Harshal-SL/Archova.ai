# Event Streaming Pattern


## chunk_id
- 1.48

## category
- architecture_patterns

## type
- pattern

## definition
- a pattern where immutable events are appended to a log and processed by consumers in order with replay support.

## when_to_use
- systems needing durable event logs and replayable processing
- multiple consumers requiring independent offsets and backfills
- near-realtime analytics and derived state pipelines

## when_not_to_use
- simple point-to-point task distribution without replay needs
- when strict low latency is required but stream processing is too heavy

## decision_signals
- need: systems needing durable event logs and replayable processing
- need: multiple consumers requiring independent offsets and backfills
- willing to accept: requires schema evolution discipline and retention planning

## advantages
- enables replay, auditing, and rebuilding derived views
- supports multiple independent consumers without coupling

## disadvantages
- requires schema evolution discipline and retention planning
- increases complexity around ordering, partitions, and reprocessing

## anti_patterns
- using this when simple point-to-point task distribution without replay needs
- use this when strict low latency is required but stream processing is too heavy
- ignoring the downside that requires schema evolution discipline and retention planning

## real_world_examples
- kafka topics for user activity and downstream analytics
- event log powering projections for cqrs read models

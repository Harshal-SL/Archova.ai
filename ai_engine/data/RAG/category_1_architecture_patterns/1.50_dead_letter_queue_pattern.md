# Dead Letter Queue Pattern


## chunk_id
- 1.50

## category
- architecture_patterns

## type
- pattern

## definition
- a pattern that routes messages that repeatedly fail processing to a separate queue for inspection and remediation.

## when_to_use
- asynchronous processing where some messages are poison pills
- preventing infinite retry loops that block normal throughput
- enabling manual or automated repair workflows for failures

## when_not_to_use
- when failures must be handled inline with immediate user feedback
- without clear runbooks for dlq monitoring and replay

## decision_signals
- need: asynchronous processing where some messages are poison pills
- need: preventing infinite retry loops that block normal throughput
- willing to accept: adds operational burden for triage and replay processes

## advantages
- protects healthy traffic from being blocked by bad messages
- improves observability and debuggability of message failures

## disadvantages
- adds operational burden for triage and replay processes
- can hide systemic bugs if dlqs are ignored

## anti_patterns
- use this when failures must be handled inline with immediate user feedback
- using this when without clear runbooks for dlq monitoring and replay
- ignoring the downside that adds operational burden for triage and replay processes

## real_world_examples
- orders that fail validation routed to dlq for review
- retry exhaustion sending messages to dlq with error metadata

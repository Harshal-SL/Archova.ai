# Cache-Aside Pattern


## chunk_id
- 1.42

## category
- architecture_patterns

## type
- pattern

## definition
- a conceptual caching pattern where the application checks cache before source-of-truth reads, then stores returned data for future requests.

## when_to_use
- read-heavy domains that benefit from cached read models
- architectures that need a generic cache interaction model independent of vendor
- architecture decisions evaluating cache consistency and invalidation tradeoffs

## when_not_to_use
- write-dominant workflows where cache churn exceeds value
- strictly consistent domains without stale-read tolerance or bypass controls

## decision_signals
- need: read-heavy endpoints with hot keys and repeated queries
- need: caches that can tolerate eventual consistency
- willing to accept: cache misses create latency spikes and database bursts

## advantages
- simple to implement and works with most datastores
- reduces database load and improves read latency

## disadvantages
- cache misses create latency spikes and database bursts
- invalidation and staleness handling are non-trivial

## anti_patterns
- using this for write-heavy systems where cache churn dominates
- using this for data that requires strict freshness without a cache bypass strategy
- ignoring the downside that cache misses create latency spikes and database bursts

## real_world_examples
- caching user profiles in redis with ttl
- caching product details behind an api layer

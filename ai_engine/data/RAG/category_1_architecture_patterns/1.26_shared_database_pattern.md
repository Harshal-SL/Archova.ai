# Shared Database Pattern


## chunk_id
- 1.26

## category
- architecture_patterns

## type
- pattern

## definition
- a pattern where multiple services or modules share a single database schema and instance.

## when_to_use
- small teams with shared ownership across domains
- strong consistency requirements across modules
- early-stage systems optimizing for simplicity

## when_not_to_use
- microservices needing independent deploy and data ownership
- systems requiring per-service scaling and isolation

## decision_signals
- need: small teams with shared ownership across domains
- need: strong consistency requirements across modules
- willing to accept: creates tight coupling through shared schema changes

## advantages
- enables cross-module transactions and strong consistency
- reduces data duplication and simplifies reporting queries

## disadvantages
- creates tight coupling through shared schema changes
- increases blast radius and slows independent evolution

## anti_patterns
- using this when microservices needing independent deploy and data ownership
- using this when systems requiring per-service scaling and isolation
- ignoring the downside that creates tight coupling through shared schema changes

## real_world_examples
- monolith modules sharing a single PostgreSQL database
- multiple services sharing a single Oracle schema in enterprises

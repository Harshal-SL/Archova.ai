# Idempotency Pattern


## chunk_id
- 1.39

## category
- architecture_patterns

## type
- pattern

## definition
- a pattern where repeating the same request produces the same outcome, preventing duplicate side effects.

## when_to_use
- payment, order, and booking operations with client retries
- at-least-once message processing and event delivery
- distributed workflows with network timeouts and retries

## when_not_to_use
- operations without stable idempotency keys or dedup storage
- read-only operations where idempotency is already guaranteed

## decision_signals
- need: payment, order, and booking operations with client retries
- need: at-least-once message processing and event delivery
- willing to accept: requires deduplication storage and retention management

## advantages
- enables safe retries and reduces duplicate writes
- improves reliability under transient failures

## disadvantages
- requires deduplication storage and retention management
- adds complexity to write paths and auditing

## anti_patterns
- using this when operations without stable idempotency keys or dedup storage
- using this when read-only operations where idempotency is already guaranteed
- ignoring the downside that requires deduplication storage and retention management

## real_world_examples
- idempotency keys for payment charge creation
- deduplicated consumer processing by message id

# Control Plane/Data Plane Architecture


## chunk_id
- 1.61

## category
- architecture_patterns

## type
- architecture

## definition
- an architecture that separates management and orchestration logic (control plane) from request or packet handling (data plane).

## when_to_use
- platforms managing many workloads, tenants, or clusters
- isolating critical request paths from slow configuration operations
- enforcing policy and rollout control independently of runtime traffic

## when_not_to_use
- small systems where a single plane is simpler and sufficient
- when control plane failures would still disrupt data plane correctness

## decision_signals
- need: platforms managing many workloads, tenants, or clusters
- need: isolating critical request paths from slow configuration operations
- willing to accept: increases system complexity and requires strong interfaces between planes

## advantages
- improves reliability by isolating fast-path serving from management
- enables safer rollouts and policy changes without impacting traffic paths

## disadvantages
- increases system complexity and requires strong interfaces between planes
- risk of drift between desired state and actual state if reconciliation is weak

## anti_patterns
- using this when small systems where a single plane is simpler and sufficient
- use this when control plane failures would still disrupt data plane correctness
- ignoring the downside that increases system complexity and requires strong interfaces between planes

## real_world_examples
- kubernetes control plane managing pods while kubelet handles runtime
- service mesh control plane pushing config to sidecar proxies

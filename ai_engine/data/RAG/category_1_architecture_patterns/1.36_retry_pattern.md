# Retry Pattern


## chunk_id
- 1.36

## category
- architecture_patterns

## type
- pattern

## definition
- a resilience pattern that repeats failed operations to handle transient errors with controlled retry policies.

## when_to_use
- transient failures like timeouts and rate limits
- idempotent operations or safe-at-least-once handlers
- network calls to dependencies with occasional blips

## when_not_to_use
- non-idempotent writes without idempotency keys
- permanent failures like validation errors and auth failures

## decision_signals
- need: transient failures like timeouts and rate limits
- need: idempotent operations or safe-at-least-once handlers
- willing to accept: can amplify load and cause retry storms

## advantages
- improves success rate under intermittent failures
- reduces user-visible errors during brief outages

## disadvantages
- can amplify load and cause retry storms
- increases latency and complicates debugging

## anti_patterns
- using this when non-idempotent writes without idempotency keys
- using this when permanent failures like validation errors and auth failures
- ignoring the downside that can amplify load and cause retry storms

## real_world_examples
- exponential backoff retries on http 503 errors
- consumer retry with backoff for message processing

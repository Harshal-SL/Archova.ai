# Reactive System Architecture


## chunk_id
- 1.64

## category
- architecture_patterns

## type
- architecture

## definition
- an architecture style focused on responsiveness, resilience, and elasticity using asynchronous message-driven communication.

## when_to_use
- highly concurrent systems needing backpressure and non-blocking i/o
- distributed systems where failures must be isolated and recovered
- systems with variable load that require elastic scaling

## when_not_to_use
- simple CRUD applications where synchronous calls are sufficient
- teams unfamiliar with async messaging and backpressure concepts

## decision_signals
- need: highly concurrent systems needing backpressure and non-blocking i/o
- need: distributed systems where failures must be isolated and recovered
- willing to accept: increases complexity in reasoning about async flows and consistency

## advantages
- improves resilience via isolation and message-driven design
- supports elasticity by decoupling components and smoothing load

## disadvantages
- increases complexity in reasoning about async flows and consistency
- testing and debugging require strong observability tooling

## anti_patterns
- using this when simple CRUD applications where synchronous calls are sufficient
- using this when teams unfamiliar with async messaging and backpressure concepts
- ignoring the downside that increases complexity in reasoning about async flows and consistency

## real_world_examples
- actor-based services handling millions of concurrent messages
- event-driven microservices with backpressure-aware pipelines

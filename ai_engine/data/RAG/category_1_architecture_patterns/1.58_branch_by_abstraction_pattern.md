# Branch By Abstraction Pattern


## chunk_id
- 1.58

## category
- architecture_patterns

## type
- pattern

## definition
- a refactoring pattern that introduces an abstraction layer so old and new implementations can run side by side behind the same interface.

## when_to_use
- replacing critical components without long-lived feature branches
- migrating databases, apis, or libraries with minimal downtime risk
- enabling gradual cutover with feature flags

## when_not_to_use
- simple changes that do not justify additional indirection
- when maintaining two implementations would be too costly

## decision_signals
- need: replacing critical components without long-lived feature branches
- need: migrating databases, apis, or libraries with minimal downtime risk
- willing to accept: adds indirection and temporary complexity to the codebase

## advantages
- reduces merge conflicts and supports incremental delivery
- enables safe rollback by switching implementations

## disadvantages
- adds indirection and temporary complexity to the codebase
- risk of divergence if both implementations evolve separately

## anti_patterns
- using this when simple changes that do not justify additional indirection
- use this when maintaining two implementations would be too costly
- ignoring the downside that adds indirection and temporary complexity to the codebase

## real_world_examples
- switching payment providers behind a common interface
- migrating from legacy auth to new identity service with toggles
